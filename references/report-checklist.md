# Report Attachment Checklist
**Ensuring Complete Project Documentation**

Before delivering any research report, verify all required attachments
are included. This checklist prevents missing artifacts that support
claims, undocumented scope changes, lost signal documentation, and an
incomplete audit trail.

---

## Core Attachments (required for all reports)

### 1. Contract & Scope Documents
- [ ] Original contract (signed, dated)
- [ ] Contract addendums (if any scope/timeline changes occurred)
- [ ] Project brief (initial scope definition)
- [ ] Final scope summary (if different from original)

**Naming convention:** `YYYY-MM-DD_Contract_v[X].pdf`

### 2. Source Library
- [ ] Source scoring sheet (every source, every dimension, band)
- [ ] Source archive (PDFs, screenshots, or links to all cited sources)
- [ ] Source metadata (publication dates, authors, access dates)

**Naming convention:** `SourceLibrary_[ProjectName]_YYYY-MM-DD.xlsx`

**Organization:**
```
/ProjectName/
  /SourceLibrary/
    Source_001_...pdf
    Source_002_...pdf
    Source_003_...png
    SourceScoringSheet.xlsx
```

### 3. Signal Documentation
- [ ] All signal entries (scope-relevant events, formatted consistently)
- [ ] Supporting artifacts (emails, screenshots, meeting notes)
- [ ] Signal summary table (quick reference of all signals with status)

**Naming convention:** `YYYY-MM-DD_Signal_[Description].pdf`

### 4. Report Quality Documentation
- [ ] Report scoring grid (completed 5-dimension evaluation — see
      `report-scoring.md`)
- [ ] Triangulation map (claim-to-source mapping — see
      `triangulation-mapping-guide.md`)
- [ ] Quality tier justification

### 5. Deliverables
- [ ] Final report (primary deliverable)
- [ ] Executive summary (if requested)
- [ ] Supplementary materials (charts, tables, data visualizations)
- [ ] Presentation deck (if requested)

**Naming convention:** `[ProjectName]_FinalReport_YYYY-MM-DD.pdf`

---

## Supplementary Attachments (include if applicable)

### 6. Communications
- [ ] Key email threads (scope discussions, feedback, approvals)
- [ ] Meeting notes (discovery calls, status updates, debrief)
- [ ] Chat logs (significant discussions)

**When to include:** if communications contain scope clarifications,
approvals, or signal documentation.

### 7. Research Process Artifacts
- [ ] Search queries log (keywords used, databases accessed)
- [ ] Source rejection log (sources evaluated but not used, with
      reasons)
- [ ] Triangulation worksheets (claim validation working documents)
- [ ] Version history (report draft iterations)

**When to include:** for complex projects where process transparency is
valuable.

### 8. Field-Specific Materials
- [ ] Business field: operational signals, strategy documents, financial
      data
- [ ] Market field: competitive analysis, market sizing, trend reports
- [ ] Human field: leadership profiles, organizational charts, culture
      artifacts
- [ ] Brand field: brand positioning maps, messaging frameworks
- [ ] Culture field: values documentation, behavior patterns, social
      proof

**When to include:** if the report makes significant claims in these
fields.

### 9. Regulatory & Compliance
- [ ] Relevant regulations (full text or summaries)
- [ ] Industry standards
- [ ] Compliance checklists

**When to include:** for compliance-focused or regulatory research.

### 10. Testimonials & Feedback
- [ ] Client testimonial (if received and permission granted)
- [ ] Revision requests (documented changes and rationale)
- [ ] Post-project debrief notes

---

## File Naming Standards

**Universal format:** `YYYY-MM-DD_[DocumentType]_[Description]_v[X].[ext]`

**Examples:**
- `2024-03-10_Contract_InitialScope_v1.pdf`
- `2024-03-25_Email_ScopeExpansion_v2.pdf`
- `2024-04-05_Report_Final_v1.pdf`
- `2024-04-08_Report_Final_v2.pdf` (after revisions)

**Why this matters:** chronological sorting works automatically, version
control is clear, no ambiguity about document purpose.

## Pre-Delivery Checklist

Before sending the final report, verify:

- [ ] All sources cited in the report are in the Source Library
- [ ] All sources in the Source Library are scored and tiered
- [ ] All signals have supporting attachments
- [ ] Report quality score is documented and justified
- [ ] Contract and all addendums are included
- [ ] File naming follows standards (dates, versions, descriptions)
- [ ] Folder structure is organized and navigable
- [ ] Requested formats are included (PDF, DOCX, PPTX, etc.)
- [ ] Confidential information is appropriately redacted (if sharing as
      a case study)
- [ ] Version control is clear (v1, v2, etc. with change notes)

---

## Delivery Format Options

**Option 1: ZIP archive** — compress the entire project folder; name
`[ProjectName]_CompletePackage_YYYY-MM-DD.zip`; include a `README.md`
with a folder navigation guide.

**Option 2: Cloud folder** — upload with appropriate permissions;
include a folder structure diagram.

**Option 3: Document management system** — follow the recipient's
naming/tagging conventions; ensure all links work within their system.

---

## Post-Delivery Checklist

After delivery, archive:

- [ ] Confirmation of receipt
- [ ] Final revision requests (if any)
- [ ] Internal debrief notes (lessons learned, process improvements)
- [ ] Backup copy (stored per data retention policy)
- [ ] Testimonial (if received)
- [ ] Invoice and payment confirmation (for financial records)

---

## Common Missing Attachments

Don't forget:
- ❌ Contract addendums (if scope changed mid-project)
- ❌ Source rejection log (shows thoroughness)
- ❌ Approval emails (protects against disputes)
- ❌ Process improvement notes (for continuous learning)
- ❌ Backup copies of time-sensitive sources (before links break)

---

## Quick Start: Minimum Viable Package

If time is limited, prioritize these five:

1. Final report (the primary deliverable)
2. Contract(s) (scope and terms)
3. Source library (scoring sheet + archived sources)
4. Signal documentation
5. Report quality score (self-evaluation)

Everything else can be added post-delivery if needed.

## Version History Section (add to report)

```markdown
## Report Version History

| Version | Date | Changes | Author |
|---------|------|---------|--------|
| v1.0 | 2024-04-05 | Initial delivery | [Name] |
| v1.1 | 2024-04-08 | Executive summary expanded; formatting updates per feedback | [Name] |
```

**Why include this:** shows professionalism and responsiveness,
documents scope of revisions, protects against "I never asked for that"
disputes.

---

**Field use:** Before delivery, run through this checklist. Check every
box. Organize files per the folder structure. Name files consistently.
Include version history in the report. Archive the complete package
post-delivery.
